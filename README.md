# Java Project Matching App

Javaの自己学習で習得した内容を使って開発した、案件マッチングアプリです。

案件情報とエンジニアのスキル・希望条件を比較し、
案件ごとのマッチスコアを確認できます。

現在は、Java基礎で作成した **Ver0.1 コンソール版** を土台に、メソッド分割・オブジェクト指向・コレクション・例外処理を反映した **Ver0.2へのリファクタリング** を進めています。

---

## 制作目的

Javaの自己学習で学んだ内容を、実際のアプリケーション開発で使用し、
基礎構文への理解を深めることを目的として制作しました。

最初から完成形のWebアプリを作るのではなく、

```text
Ver0.1
Java基礎によるコンソール版
↓
Ver0.2
オブジェクト指向版
↓
Ver1.0
Webアプリ版
```

のように、Javaの学習段階に合わせて同じアプリを段階的に発展させる予定です。

## データ管理

Ver0.1完成時は、案件情報やエンジニアのスキル情報を複数の平行配列で管理していました。

その後、オブジェクト指向の学習内容を反映し、現在は `Project`、`Engineer`、`Skill` クラスを使用して管理しています。

### Project

1件の案件情報を管理します。

```java
List<Project> projects = new ArrayList<>();
```

各 `Project` オブジェクトは、以下の情報を保持します。

- 案件名
- 必須スキル
- 尚可スキル
- 必要経験年数
- 勤務地
- リモート可否

### Engineer

1人のエンジニア情報を管理します。

- 希望勤務地
- リモート希望
- 保有スキル

### Skill

1つのスキルに関する経験情報を管理します。

```java
List<Skill> skills;
```

各 `Skill` オブジェクトは、以下の情報を保持します。

- スキル名
- 経験区分
- 実務経験年数

例えば、Javaのスキル情報は以下のように1つのオブジェクトとして扱います。

```java
new Skill("Java", 1, 0)
```

現在の構造は、概ね以下のようになっています。

```text
Engineer
├─ preferredLocation
├─ remotePreferred
└─ List<Skill> skills
   ├─ Skill("Java", 1, 0)
   ├─ Skill("React", 2, 1)
   ├─ Skill("TypeScript", 2, 1)
   ├─ Skill("PostgreSQL", 2, 1)
   └─ Skill("Linux", 2, 1)
```

この変更により、Ver0.1で使用していた平行配列を解消し、関連するデータをオブジェクト単位で管理できるようにしました。

## マッチスコア

案件ごとに100点満点で計算します。

| 評価項目 | 最大点 |
|---|---:|
| 必須スキル | 50点 |
| 尚可スキル | 15点 |
| 実務経験年数 | 15点 |
| 勤務地 | 10点 |
| リモート条件 | 10点 |
| 合計 | 100点 |

### 必須スキル

- 実務経験あり：50点
- 学習経験のみ：25点
- スキルなし：0点

### 尚可スキル

- 実務経験あり：15点
- 学習経験のみ：8点
- スキルなし：0点

### 実務経験年数

必要経験年数を満たしている場合は15点です。

必要年数を満たしていない場合は、

```text
実務経験年数 × 15 ÷ 必要経験年数
```

で部分点を計算します。

学習経験のみの場合は、実務経験年数としては扱いません。

## 学習したこと・振り返り

### Java基礎を実際の処理に使う

Javaの基礎を学習した後、その内容を使って実際に動くものを作ってみたいと考え、本アプリの開発を始めました。

まだJava学習の初期段階のため、Ver0.1はコンソールアプリとして制作しています。

実装方法を調べたりAIのサポートを利用したりしながら進めていますが、
完成コードをそのまま使用するのではなく、まず自分で処理を考えてから実装することを意識しています。

実際にコードを書くことで、教材を見ているだけでは気付かなかった部分を理解する機会が増えました。

### boolean型への理解

リモート可能案件を絞り込む際、当初は以下のように書いていました。

```java
if (remoteAvailable[i] == true) {
```

しかし、`remoteAvailable[i]` 自体が `boolean` 型であるため、

```java
if (remoteAvailable[i]) {
```

だけで同じ判定ができることを理解しました。

構文として使用できることと、その型や仕組みを理解して使用できることは別だと感じた部分で、
boolean型について改めて理解を深めるきっかけになりました。

### マッチスコア計算

Ver0.1の中で最も難しかったのが、マッチスコアの計算処理です。

まず、

```text
案件をfor文で1件ずつ処理
↓
案件ごとにscoreを0へ初期化
↓
各条件をif文で判定
↓
条件に応じてscoreへ加点
```

という流れに分解すると、処理を考えやすくなりました。

一方で、必須・尚可スキルについては、

- スキルを保有しているか
- 実務経験か学習経験か

を判定する必要があります。

さらに経験年数では、

- 必須スキルがエンジニアのどのスキルに対応するか
- 実務経験があるか
- 必要経験年数を満たしているか
- 不足している場合に何点与えるか

まで考える必要があり、複数の条件を組み合わせる難しさを感じました。

特に最初は、

```text
案件の添字 i
```

と、

```text
エンジニアのスキルの添字
```

を同じものとして比較してしまっていました。

その後、

```text
i = 案件を処理するための添字
j = エンジニアのスキルを探すための添字
```

として役割を分け、
案件の必須スキルをエンジニアのスキル一覧から検索してから、
そのスキルの経験区分や実務経験年数を確認するよう修正しました。

この実装を通して、for文やif文を単体で理解するだけでなく、
複数の配列や条件を組み合わせて処理する考え方を学ぶことができました。

### メソッド分割とオブジェクト指向へのリファクタリング

Ver0.1完成後、メソッドとオブジェクト指向の学習内容を既存アプリへ適用しました。

まず、`main`メソッドにまとまっていた処理を、役割ごとに以下のようなメソッドへ分割しました。

- 案件一覧表示
- 必須スキル検索
- リモート可能案件表示
- 案件詳細表示
- マッチスコア計算
- マッチレベル判定

その後、平行配列で管理していたデータをクラスへ移行しました。

```text
平行配列
↓
Project / Engineer / Skill オブジェクト
```

特にエンジニアのスキル情報は、

```java
String[] engineerSkills;
int[] experienceTypes;
int[] skillYears;
```

という3つの平行配列から、まず `Skill` オブジェクトとしてまとめ、その後コレクションの学習内容を反映して、現在は以下のように管理しています。

```java
List<Skill> skills;
```

これにより、スキル名・経験区分・経験年数を1つの `Skill` オブジェクトとして扱いながら、複数のスキルを `List` として管理できるようになりました。

今回のリファクタリングを通して、クラスを新しく作るだけでなく、既存の処理を維持しながらデータ構造を段階的に変更する考え方を学びました。

### コレクションと拡張for文の適用

オブジェクト指向の学習後は、配列で管理していた案件・スキル情報を `List` / `ArrayList` へ変更しました。

例えば案件情報は、

```java
List<Project> projects = new ArrayList<>();
```

として管理し、案件の追加には `add()`、件数の取得には `size()`、特定要素の取得には `get()` を使用しています。

また、マッチスコア計算でエンジニアのスキルを1件ずつ確認する処理では、添字を使用する必要がないため、

```java
for (Skill skill : engineer.skills) {
    // スキル情報を確認
}
```

という拡張for文へ変更しました。

通常のfor文と拡張for文は、単に短く書けるかではなく、添字が必要かどうかを考えて使い分けることを学びました。

### 例外処理による入力チェック

メニュー番号の入力では、入力文字列を `Integer.parseInt()` で数値へ変換しています。

数値以外や空文字が入力された場合は `NumberFormatException` が発生するため、`try-catch` を追加しました。

```java
try {
    number = Integer.parseInt(numberStr);
} catch (NumberFormatException e) {
    System.out.println("\n不正な値が入力されました。");
    System.out.println("Enterキーを押すとメニューに戻ります。");
    scanner.nextLine();
    continue;
}
```

例外が発生する可能性のある処理だけを `try` で囲み、`catch` では案内を表示したうえで `continue` によりメニュー処理を継続するようにしました。

これにより、不正な入力があってもアプリが例外終了せず、再度操作を続けられるようになりました。
