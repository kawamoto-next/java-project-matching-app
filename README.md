# Java Project Matching App

Javaの自己学習で習得した内容を使って開発した、案件マッチングアプリです。

案件情報とエンジニアの保有スキル・実務経験年数・希望条件を比較し、
案件ごとのマッチスコアを100点満点で算出します。

Java基礎で作成した **Ver0.1 コンソール版** を土台に、
メソッド、オブジェクト指向、コレクション、例外処理などの学習内容を反映しながらリファクタリングを行い、
**Ver0.2 オブジェクト指向版まで完成**しています。

> 本アプリに登録されている案件、企業、人物などの情報は、すべて学習用に作成した架空のサンプルデータです。実在する企業・人物・案件とは関係ありません。

## 制作目的

Javaの自己学習で学んだ内容を実際のアプリケーション開発へ適用し、
基礎構文だけでなく、オブジェクト指向、クラス設計、データ管理、責務分離について理解を深めることを目的として制作しました。

最初から完成形のWebアプリを作るのではなく、

```text
Ver0.1
Java基礎によるコンソール版
↓
Ver0.2
メソッド・オブジェクト指向などを反映したJava版
↓
Ver1.0
Webアプリ版
```

のように、Javaの学習段階に合わせて同じアプリを段階的に発展させています。

開発では、完成速度だけではなく、

- 学習した内容を実際のコードへ反映する
- 実装した処理を自分の言葉で説明できる
- 既存機能を維持しながら段階的にリファクタリングする
- 変更内容と学習過程をGitHubへ残す

ことを重視しています。

## 各クラスの役割

### Main

アプリケーションの起動とコンソール操作を担当します。

主な役割：

- サンプル案件の作成
- エンジニア情報の作成
- メニュー表示
- ユーザー入力受付
- 案件一覧表示
- 必須スキル検索
- リモート可能案件表示
- マッチスコア表示

---

### Project

1件の案件情報を管理します。

保持する情報：

- 案件名
- 案件スキル一覧
- 勤務地
- リモート可否

案件に設定されているスキルは、

```java
List<ProjectSkill>
```

として管理しています。

また、案件には必須スキルが1件以上必要であるため、
`Project` の生成時および `setProjectSkills()` による変更時にバリデーションを行います。

必須スキルが1件も存在しない場合は、

```java
IllegalArgumentException
```

を発生させ、不正な状態の案件が作成されないようにしています。

---

### ProjectSkill

案件に設定される1つのスキル条件を管理します。

保持する情報：

- スキル名
- 必須 / 尚可
- 必要実務経験年数

必須・尚可は定数で管理しています。

```java
public static final int REQUIRED = 1;
public static final int OPTIONAL = 2;
```

---

### Engineer

1人のエンジニア情報を管理します。

保持する情報：

- 希望勤務地
- リモート希望
- 保有スキル一覧

保有スキルは、

```java
List<Skill>
```

として管理しています。

---

### Skill

エンジニアが保有する1つのスキルについて管理します。

保持する情報：

- スキル名
- 経験区分
- 実務経験年数

経験区分は定数で管理しています。

```java
public static final int LEARNING_ONLY = 1;
public static final int PRACTICAL_EXPERIENCE = 2;
```

---

### MatchCalculator

案件情報とエンジニア情報を比較し、
マッチスコアとマッチレベルを算出します。

スコア計算処理を `Main` から分離することで、

```text
Main
→ アプリの起動・入力・表示

MatchCalculator
→ マッチング処理
```

のように役割を分けています。

## マッチスコア

案件ごとに最大100点で計算します。

| 評価項目 | 最大点 |
|---|---:|
| 必須スキル＋経験年数 | 50点 |
| 尚可スキル | 30点 |
| 勤務地 | 10点 |
| リモート条件 | 10点 |
| 合計 | 100点 |

必須スキルと経験年数は別々に加点せず、
1つの評価項目として計算します。

---

## 必須スキル＋経験年数

各必須スキルについて、エンジニアの経験状況から係数を算出します。

| エンジニアの状態 | 係数 |
|---|---:|
| スキルなし | 0.0 |
| 学習経験のみ | 0.5 |
| 実務経験あり・必要年数指定なし | 1.0 |
| 実務経験あり・必要年数指定あり | 経験年数に応じて計算 |

実務経験があり、必要実務経験年数が指定されている場合は、

```text
0.5 + 0.5 × (実務経験年数 ÷ 必要経験年数)
```

で係数を計算します。

係数の上限は `1.0` とします。

例えば案件条件が、

```text
Java 実務3年以上
```

の場合、

```text
スキルなし     → 0.0
学習経験のみ   → 0.5
実務1年        → 約0.6667
実務2年        → 約0.8333
実務3年以上    → 1.0
```

となります。

複数の必須スキルがある場合は、

```text
必須スキル点
= 必須スキルの係数合計
  ÷ 必須スキル数
  × 50
```

で計算します。

そのため、必須スキル数が増えても最大点は50点です。

---

## 尚可スキル

尚可スキルは以下の係数を使用します。

| エンジニアの状態 | 係数 |
|---|---:|
| 実務経験あり | 1.0 |
| 学習経験のみ | 0.5 |
| スキルなし | 0.0 |

複数の尚可スキルがある場合は、

```text
尚可スキル点
= 尚可スキルの係数合計
  ÷ 尚可スキル数
  × 30
```

で計算します。

例えば、

```text
Linux       → 実務経験あり → 1.0
Java        → 学習経験のみ → 0.5
Spring Boot → スキルなし   → 0.0
```

の場合、

```text
(1.0 + 0.5 + 0.0) ÷ 3 × 30
= 15点
```

となります。

尚可スキルが0件の場合は0点とし、
30点を他の評価項目へ再配分しません。

---

## 勤務地

エンジニアの希望勤務地と案件勤務地が一致する場合、

```text
10点
```

を加算します。

一致しない場合は0点です。

---

## リモート条件

現在のコンソール版では、
エンジニアがリモート勤務を希望している場合、

```text
案件がリモート対応 → 10点
案件がリモート不可 → 0点
```

としています。

リモート勤務を希望していない場合は、
案件条件にかかわらず10点としています。

---

## 小数の扱い

スコアの途中計算では `double` を使用します。

係数や各項目の点数について途中で四捨五入せず、
小数を保持したまま合計します。

最終的な合計スコアのみ、

```java
Math.round()
```

を使用して整数へ四捨五入します。

---

## マッチレベル

最終的に四捨五入した整数のスコアを使用して、
以下の3段階で判定します。

| スコア | 判定 |
|---|---|
| 80〜100点 | 高マッチ |
| 60〜79点 | 候補 |
| 0〜59点 | 低マッチ |

---

## バリデーション

案件には必須スキルを1件以上設定する必要があります。

`Project` クラスでは、
案件生成時とスキル一覧変更時の両方で必須スキルの存在を確認します。

```text
projectSkillsを1件ずつ確認
↓
REQUIREDが存在するか確認
↓
1件以上存在する
→ 正常

1件も存在しない
→ IllegalArgumentException
```

これにより、

```text
尚可スキルだけの案件
```

が作成されることを防いでいます。

## マッチスコアの確認ケース

マッチスコアについて、複数の条件を一時的に変更し、
手計算した結果と実際の実行結果が一致することを確認しました。

### 複数必須・複数尚可

複数の必須スキル・尚可スキルを設定し、
各係数の平均から得点が計算されることを確認しました。

### 必要経験年数不足

実務経験1年 / 必要3年の場合、

```text
0.5 + 0.5 × (1 ÷ 3)
```

による部分点が計算されることを確認しました。

実務経験2年 / 必要3年の場合も、

```text
0.5 + 0.5 × (2 ÷ 3)
```

による部分点が計算されることを確認しました。

### 必要経験年数指定なし

実務経験あり・必要経験年数0の場合に、
係数が `1.0` となり、0除算が発生しないことを確認しました。

### 係数の上限

実務経験年数が必要経験年数を上回る場合でも、
係数が `1.0` を超えないことを確認しました。

### 必須スキル3件

以下の係数を持つ必須スキル3件について、

```text
1.0
0.5
0.0
```

必須スキル点が、

```text
(1.0 + 0.5 + 0.0) ÷ 3 × 50
= 25点
```

となることを確認しました。

### 尚可スキル0件

尚可スキルが存在しない場合、
尚可スキル点が0点となり、
他の評価項目へ30点が再配分されないことを確認しました。

### 尚可スキルの混在

```text
実務経験あり
学習経験のみ
スキルなし
```

が1件ずつ存在する場合、

```text
(1.0 + 0.5 + 0.0) ÷ 3 × 30
= 15点
```

となることを確認しました。

### 必須スキル0件

必須スキルが0件の場合、

```text
IllegalArgumentException
```

が発生し、不正な `Project` を作成できないことを確認しました。

また、生成済みの `Project` に対して `setProjectSkills()` を使用した場合も、
必須スキル0件へ変更できないことを確認しました。

### 四捨五入とマッチレベル

以下の境界値を確認しました。

```text
59.4 → 59点 → 低マッチ
59.5 → 60点 → 候補
79.4 → 79点 → 候補
79.5 → 80点 → 高マッチ
```

これにより、
途中計算では小数を保持し、
最終スコアを四捨五入した後にマッチレベルを判定できていることを確認しました。

## 学習したこと・振り返り

### 平行配列からオブジェクト管理への変更

Ver0.1では、
案件情報やエンジニアのスキル情報を複数の配列で管理していました。

オブジェクト指向の学習後、

```text
平行配列
↓
Project / Engineer / Skill / ProjectSkill
```

へ変更しました。

これにより、
関連するデータを1つのオブジェクトとして扱えるようになり、
データ同士の関係を把握しやすくなりました。

---

### Listを利用した複数スキル対応

当初は1案件につき、

```text
必須スキル1件
尚可スキル1件
```

という構造でした。

Ver0.2では `Project` が、

```java
List<ProjectSkill>
```

を保持する構造へ変更し、

```text
必須スキル複数件
尚可スキル複数件
```

を扱えるようにしました。

スキル数が増えても最大点が増えないよう、
各スキルの係数の平均から点数を算出しています。

---

### 経験年数を含むマッチング

Ver0.1では、

```text
必須スキル
経験年数
```

を別々の評価項目として扱っていました。

Ver0.2では、
必須スキルの経験区分と必要実務経験年数を組み合わせて評価する方式へ変更しました。

これにより、

```text
スキルなし
学習経験のみ
実務経験あり・必要年数不足
実務経験あり・必要年数達成
```

を区別して評価できるようになりました。

---

### クラスの責務分離

当初は `Main` に多くの処理が集中していました。

現在は、

```text
Main
→ アプリ起動・入力・表示

model
→ データ管理

MatchCalculator
→ マッチング計算
```

という形に役割を分けています。

また、

```text
app
model
service
```

のパッケージへ分割することで、
クラス数が増えても役割を把握しやすい構成へ変更しました。

---

### バリデーション処理

必須スキルが存在しない案件を作成できてしまう問題に対して、
`Project` クラスへバリデーション処理を追加しました。

チェック処理を専用メソッドへ分離し、

```text
コンストラクタ
setProjectSkills()
```

の両方から呼び出すことで、
同じチェック処理を重複して記述せずに再利用できるようにしました。

この実装を通して、
データが不正な状態になってから対処するのではなく、
不正な状態そのものを作らせないという考え方を学びました。

---

### 境界値を意識した動作確認

係数上限
尚可0件
必須0件
59点 / 60点

実装した計算式を手計算した結果と実行結果を比較することで、
